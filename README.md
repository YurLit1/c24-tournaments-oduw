## 2. Проєкт (О1.1)

Гравці реєструються на турнір з обмеженою кількістю місць, організатор фіксує результати матчів. Головна складність: реєстрація відкривається, і місця розбирають за хвилину.

**Ролі:** гравець (`user`) реєструється на турнір і бачить свої реєстрації; організатор (`staff`) фіксує результати матчів. До ЛР3 користувач передається заголовком `X-User-Id`.

**Головна операція:** `POST /v1/registrations` - реєстрація з утриманням місця.

**Сутності:** `tournament` (турнір, місця `slots` і вільні `available`, внесок), `registration` (гравець + турнір + нікнейм), `match` (пара реєстрацій, переможець), `app_user` (гравець або організатор).

**Стани реєстрації:**

```mermaid
stateDiagram-v2
  [*] --> held: реєстрація (місце списано)
  held --> confirmed: внесок сплачено
  held --> expired: минув expires_at (місце повернуто)
  held --> cancelled: відмова (місце повернуто)
  confirmed --> cancelled: відмова (місце повернуто)
```

Матч: `scheduled → finished`, результат фіксується один раз.

**Інваріанти:**

1. Учасників не більше, ніж місць: `0 ≤ available ≤ slots`.
2. Один гравець - одна активна (`held` / `confirmed`) реєстрація на турнір; нікнейм унікальний серед активних реєстрацій турніру.
3. Результат матчу фіксується один раз.
4. Власник реєстрації - користувач із `X-User-Id`, а не з тіла запиту.

**Параметри (навчальні припущення):** 64 місця (тестовий турнір CS2 - 2 місця), внесок 5000 копійок = 50,00 UAH (`bigint` + валюта), утримання місця 15 хвилин, нікнейм 3–32 символи, реєстрація до `starts_at`. Моменти - `timestamptz`, назва часової зони турніру - окреме поле `time_zone`.

## 3. Архітектура

```mermaid
flowchart LR
  client["Клієнт :8081"] --> nginx["nginx :8080<br/>least_conn"]
  nginx --> appa["app-a"]
  nginx --> appb["app-b"]
  appa --> pg[("PostgreSQL")]
  appb --> pg
  migrate["migrate"] --> pg
```

Шлях головної операції - одна транзакція PostgreSQL:

1. `INSERT INTO idempotency_key … ON CONFLICT …` - ключ ідемпотентності (користувач, операція, ключ, відбиток тіла). Ключ уже є: те саме тіло → збережена відповідь, інше тіло → 422, запит із цим ключем ще виконується → 409.
2. `UPDATE tournament SET available = available - 1 WHERE id = … AND registration_open AND available > 0 AND starts_at > now() RETURNING id` - перевірка й списання місця однією атомарною дією.
3. Рядка немає: турніру немає → 404, інакше місць немає → 409.
4. `INSERT INTO registration … 'held'`; порушення унікальності → 409, невідомий користувач → 422. Помилка відкочує предметну зміну до точки збереження, місце повертається.
5. `UPDATE idempotency_key SET state = 'done', …` зберігає код і тіло відповіді; COMMIT, лише після нього - `201` + `Location` або відмова.

Решта сервісів комплекту (Kafka, Redis, Keycloak, шлюзи, симулятор, Prometheus, Grafana) призначені для ЛР4–ЛР6 і поки не використовуються.

## 5. Збирання й запуск

Потрібен Docker Desktop із Compose v2 (від 6 ГБ пам'яті для Docker). Команди - з кореня репозиторію, у Git Bash.

```bash
cp .env.example .env
docker compose up -d --build
```

Міграції застосовує сервіс `migrate`. Повне скидання бази - `docker compose down -v`.

Клієнт - окремо, не в Compose:

```bash
py -m http.server 8081 --bind 127.0.0.1 --directory client
```

Відкрити http://localhost:8081.

Тестові дані: гравці `u-player1`, `u-player2`, `u-player3` (логіни `player1`…`player3`, пароль `player-pass`), організатор `u-organizer` (`organizer` / `organizer-pass`); турніри `t-dota` (64 місця, 50,00 UAH) і `t-cs2` (2 місця). Для досліду гонки: турнір `t-race` (64 місця) і гравці `u-race001`…`u-race200`.

### ЛР2. Конкуренція та повторення запитів

| Пункт | Де реалізовано | Перевірка та свідчення |
| --- | --- | --- |
| О2.1 Інваріант за одночасних запитів | `server/app/registrations.py` (умовний `UPDATE`), `tools/race.py` | `py tools/race.py`: 200 одночасних запитів на 64 місця через `app-a` і `app-b` → `201 - 64`, `409 - 136`, `available = 0`, активних реєстрацій 64 |
| О2.2 Механізм ідемпотентності | `server/app/idempotency.py`, `migrations/002_idempotency.sql` | `bash tools/check-lab2.sh`: немає ключа → 400, повтор через інший екземпляр → та сама відповідь, інше тіло → 422, ключ ще обробляється → 409, прострочені ключі прибрано |

**О2.1, вибір способу.** Інваріант тримає атомарний умовний запис: одна інструкція `UPDATE … WHERE available > 0` і перевіряє залишок, і списує місце. Блокування рядка турніру бере сама інструкція; одночасний запит з іншого екземпляра чекає на COMMIT і перевіряє умову вже на новому значенні `available`. Окремий `SELECT … FOR UPDATE` дав би той самий результат за два звернення до бази замість одного. Серіалізовна транзакція потребувала б повторів після помилок серіалізації, а під час розпродажу місць їх було б багато. `CHECK (available BETWEEN 0 AND slots)` лишається другим рубежем. Локальний м'ютекс не підходить, бо екземплярів два.

**О2.2, як працює.** Заголовок `Idempotency-Key` (8–128 символів) обов'язковий для `POST /v1/registrations`, без нього 400. Рядок `idempotency_key` (користувач, операція, ключ, відбиток тіла, стан, код, `Location`, відповідь, строк 24 години) вставляється й завершується в одній транзакції з предметною зміною, тому ключ без реєстрації або реєстрація без ключа неможливі. Наявність ключа не перевіряється окремим `SELECT`: рішення приймає `INSERT … ON CONFLICT` за первинним ключем. Відбиток - SHA-256 від JSON перевіреного тіла з відсортованими ключами, перестановка полів його не змінює. Зберігаються й відмови (404, 409): повтор повертає ту саму відмову. Якщо перший запит із цим ключем ще не зафіксовано, другий чекає до 500 мс (`lock_timeout`) і отримує 409 з `Retry-After: 1`. Прострочені ключі кожен екземпляр прибирає раз на 30 с порціями по 500 рядків (`FOR UPDATE SKIP LOCKED`).

## 8. Межі гарантій

Інваріант «учасників не більше, ніж місць» тримають умовний `UPDATE` в одній транзакції та `CHECK (available BETWEEN 0 AND slots)`. Повтор із тим самим ключем не повторює предметну зміну, поки ключ зберігається (24 години); після цього той самий ключ вважається новим. Керована відмова між COMMIT і відповіддю (О2.3) та повтори в клієнті (О2.4) до виконаних пунктів не входять. Завершення строку `held` - у ЛР4.
